# SAMTokEdit：反事实孪生编辑数据需求

- **日期**：2026-10-14。
- **读者**：数据侧，即 SA-1B 数据管线（仓库 `sam3-crispedit`，分支 `sa1b-samtok-edit-data`）。
- **一句话**：在同一张源图上，找两个同类实例，用**同一句 no-ref 指令**分别编辑，得到两张不同的目标图。这样模型只有读懂 prompt 里的 mask token，才能知道该改哪一个。
- **与现有数据的关系**：是 50k SA-1B 数据（`datasets/sa1b_samtok_edit_50k_20261014/`）的一个补充子集，规模约为它的十分之一。生成和审核沿用 50k 的流程，主要改动在"选实例"和"规划"两步，另外加几条组级检查。
- **依据**：方法侧的分析见 [03 v3 优化计划与进度](03_SAMTokEdit_Qwen21_v3优化计划与进度.md)；协议见 benchmark（v2branch）的协议文档，共享盘副本 `datasets/samtok_edit_benchmark_v2/docs/INSTRUCTION_PROTOCOL_ZH.md`（指令协议 1.0、mask 语义 1.1）。

---

## 1. 为什么需要这份数据

### 1.1 现有数据的退路

50k 数据里，每个 mask 单独规划一种编辑。所以同一张源图上的两条样本，指令文字几乎总是不同的：

| 源图 | 样本 1 | 样本 2 |
|---|---|---|
| 一张街景 | `Remove the selected umbrella.` | `Change the color of the selected window frame to green.` |

模型只看文字（"umbrella" 还是 "window frame"、删还是改色）就能分清要改哪里，并不需要去读 mask token。这条退路正是 v2 失败的原因：只用普通编辑对训练出来的 DiT 基本不看 token。同图同句只换 token 时，它的跟随率只有 0.06（文档 02 §4.2）。

### 1.2 孪生数据去掉退路

| | 实例 A | 实例 B |
|---|---|---|
| no-ref 指令 | `Change the color of the selected T-shirt to red.` | **逐字相同** |
| 模型实际看到的输入 | 源图 + 上句 + ⟨M_A⟩ | 源图 + 上句 + ⟨M_B⟩ |
| 目标图 | T_A：只有左边男士的 T 恤变红 | T_B：只有右边男士的 T 恤变红 |

两条输入只差 token，两张目标图却不同。模型要同时做对这两条，只能靠读 token。

### 1.3 用途

1. **训练**：两条放进同一个 batch，作为阶段 B 里"跟着 token 编辑"最直接的监督。
2. **评测**：留出一部分组，衡量"换 token 后编辑是否跟着换"。现在只有 remove 有这样的探针，而且没有标准答案；有了这份数据可以扩展到四类操作，并且有目标图可以对照。

## 2. 一组样本的定义

- **一组**：1 张源图、2 个（少数 3 个）同类实例、1 份共用的编辑语义，以及每个实例各自的 ref、源 mask、执行区域和目标图。
- **组内共用**：操作类型、scope、payload、属性、附着关系，以及由它们渲染出的 no-ref 句子。
- **组内各自独有**：ref 短语（以及由它渲染出的 ref 句子）、源 mask、执行区域、目标图、审核结果。
- **每张目标图只改一个实例。** 其余实例必须与源图一致。
- **可选的合并目标**：把组内所有成员的编辑合在一张图上（见 5.3 节），用于多指令训练。不是必需项。

## 3. 怎样选实例

### 3.1 必须满足

1. **同一种 scope。** 两个实例在 no-ref 里用同一个名词，例如都是 `T-shirt`，都是 `chair`，都是 `front wheel`。只是类别相近不算，比如 `chair` 和 `stool`。
2. **都清晰可辨。** 两个都能单独用 ref 唯一地说出来，主体可见，不是严重失焦或几乎被挡住的碎片。
3. **互不重叠，执行区域也不重叠。** 各自扩出执行区域（50k 的 `target_plus_collar` 规则）之后，两个执行区域之间仍有间隔。建议间隔不小于两者中较小实例短边的 10%，且不少于 16 像素。这样两张目标图互不影响，也能合成合并目标。
4. **大小相近。** 两者面积比不超过 3。
5. **mask 质量合格。** 沿用 benchmark 的 mask 要求：保留可见像素和孔洞；不把整个人当成衣服；不覆盖邻近物体。
6. **与 benchmark 的 200 张源图不重叠。** 沿用 50k 的排除规则：按源图 ID 和原图字节哈希排除。

### 3.2 优先选的（越难越有价值）

- 外观相似的实例：同色同款的两把椅子、穿同样衣服的两个人。
- 位置相邻的实例：并排的两扇窗、相邻的两个人。
- **不同宿主上的同类部件**：两个人的袖子、两辆自行车的前轮。benchmark 大量考的是这种部件级目标。
- **同一宿主上的同类部件**：同一个人的左右袖子、同一扇门的两个把手。这类最难，但必须能用 image-left、image-right 之类的写法唯一指代。

### 3.3 必须排除

- **纹理类、成片的同类小物**：stone、stones、leaf、leaves、brick、tile、grass 等。统计已展开的 256 张源图，同类候选对里数量最多的正是这些类别，它们几乎无法做有意义的单独编辑。
- 一堆或一束同类物（按此前定的规则，算一个物体），不能拆成两个实例。
- 天空、地面、墙面这类背景大面。
- 同一个实物的碎块：被遮挡分成两块的同一物体只算一个实例，不能凑成一组。
- 删除不自然的部件，例如人的手臂、头。这一条与 50k 的 remove 规则相同。

### 3.4 尺寸与类别的分布

| 指标 | 目标 |
|---|---|
| 较小实例的面积占图 | 约 30% 小于 0.5%，40% 在 0.5–2%，30% 大于 2%。benchmark 的面积中位数是 0.57% |
| 部件级组（scope 是部件，例如 sleeve、handle、wheel） | 不少于 40% |
| 同一宿主上的同类部件 | 约 10% |
| 单个 scope 的占比 | 不超过 5%。避免被 person、window 之类的高频类别占满 |
| 每张源图 | 最多贡献 2 组，保证源图多样 |

## 4. 指令与标注

### 4.1 总要求

- 完全遵循指令协议 1.0、mask 语义 1.1、写作风格 `benchmark-concise-2-direct-add-1`，与 50k 数据和 benchmark 一致。
- **一组只做一次规划。** 规划模型同时看到组内全部实例（例如在裁图上用两种颜色分别标出 A 和 B），输出：
  - 一份**共用**的 `instruction_spec`（ref 字段除外）；
  - 每个实例各自的 ref。
- 共用的编辑必须**对每个实例都自然成立**。只适合其中一个时，拒绝这一组，不要硬造，也不要悄悄换成别的操作。
- no-ref 句子由共用的 spec 渲染，所以组内天然逐字相同；ref 句子由各自的 ref 渲染。
- 各自的 ref 要在组内互相区分：A 的 ref 不能同时指得通 B。
- payload 的值（新颜色、替换物、新增物）组内相同。这正是关键：同一个要求，作用在哪里只由 token 决定。

### 4.2 四类操作的写法

| 操作 | 共用的 no-ref 句子（示例） | 各自的 ref 句子（示例） | 要求 |
|---|---|---|---|
| attribute | `Change the color of the selected backpack to bright yellow.` | `…of the backpack on the left girl…` / `…of the backpack on the right girl…` | 新值要与两个实例原本的颜色都明显不同；不要选与其中一个原色相同的值 |
| replace | `Replace the selected stool with a wooden bar chair.` | `Replace the stool nearest the counter with…` / `Replace the stool by the window with…` | 替换物对两个位置的空间、支撑、视角都合适 |
| remove | `Remove the selected parked bicycle.` | `Remove the parked bicycle in front of the red door.` / `…in front of the shop window.` | 两个实例都适合删除，删除后的背景都能自然补全 |
| add | `Add a red knit beanie to the selected man.` | `…to the man on image-left.` / `…to the man on image-right.` | 两个宿主都是直接承载物（协议的直接锚点）；附着关系和位置对两者都成立。不使用参照式 add |

### 4.3 三实例组（可选，约占 15%）

规则与两实例相同，三个实例两两满足第 3 节的条件。一张源图上的三个 token 可以用于多指令训练和更难的评测。

## 5. 生成

### 5.1 沿用 50k 的流程

- 每个成员单独生成一次：围绕执行区域裁图，带区域权重编辑，按执行区域羽化贴回。
- 编辑器配置、40 步采样、内部编辑提示、执行区域规则都与 50k 相同。
- 组内各成员使用**相同的 seed**，使目标图之间的差别只来自"改哪个实例"。
- 生成时用各自的 ref 句子做编辑提示，与 50k 一致。训练时用 no-ref 句子加 token。

### 5.2 贴回带来的保证

因为是按执行区域贴回，T_A 里 B 的区域与源图逐像素相同，反过来也一样。这一点不需要额外检查，但要在记录里保留各自的执行区域和"区域外改动比例"，证明它成立。

### 5.3 合并目标（可选）

- **做法**：在源图上依次贴入每个成员的执行区域，得到一张"所有成员都改了"的图。
- **前提**：各执行区域互不重叠，并满足 3.1 节第 3 条的间隔。
- **注意**：这张图不再单独调用生成模型，所以要单独记一条"合并目标"，并在审核里检查边界处是否有光影冲突（第 6 节）。

## 6. 审核

### 6.1 单条审核：与 50k 相同

每个成员的目标图分别过一遍 50k 的确定性检查和 27B 语义审核：
- 目标是否完成；
- 非目标是否保持；
- 是否自然；
- 操作是否正确。

### 6.2 组级检查：新增

| 检查 | 要求 | 方式 |
|---|---|---|
| 句子相同 | 组内 no-ref 句子逐字相同；scope、操作、payload 相同 | 确定性 |
| 指代唯一 | A 的 ref 不能指向 B，反之亦然 | 27B 审核：给出全图和一个 ref，问它指的是标出的哪一个实例 |
| 都改了 | 每张目标图在自己的源 mask 内都有明显改动（不能一个改了、一个几乎没动） | 确定性：区域内改动比例，阈值与 50k 的 `inside_changed_fraction` 口径一致 |
| 改对了实例 | T_A 里 A 被改、B 不变；T_B 相反 | 确定性（贴回已保证另一实例不变）+ 27B 审核看完成度 |
| 结果可比 | 两张目标图的编辑效果相当，例如都变成了同一种黄色，替换物是同一种东西 | 27B 审核：把两张目标图的局部并排给它看 |
| 合并目标（若有） | 边界处无光影冲突、无断裂 | 27B 审核 + 抽查 |

**判定**：任一成员没有通过单条审核，或者任一组级检查不过，**整组丢弃**。单条合格的成员可以并入普通的 50k 池，但不再作为孪生组。

### 6.3 人工抽查

自动审核会误判（50k 验证批里，规划、成图目视、自动审核三项都通过的只有 66.7%）。发布前请按操作类型分层，抽查至少 200 组，记录指代、完成度和非目标保持三项的人工结论。评测留出部分（第 8 节）要**全部**人工过一遍。

## 8. 规模、划分与交付

| 项 | 要求 |
|---|---|
| 规模 | 训练 5,000 组（约 1 万张目标图），评测 500 组 |
| 操作类型 | 四类各约 25% |
| 评测划分 | 评测组的源图与训练组、与 50k 数据的源图**都不重叠**；评测组每组都经过人工确认 |
| 交付目录 | 按数据放置约定，在 `datasets/` 下新建一个子目录，例如 `datasets/sa1b_samtok_edit_twins_<日期>/`（尚不存在，待建），包含 `final/twins_train.jsonl`、`final/twins_eval.jsonl` 和 README |
| 估计耗时 | 50k 文档记载的生图吞吐约为每机每小时 737 条原始结果，4 机约 2,900 条。1.1 万张目标图的生成约 4–5 小时；加上规划和冷启动，按 6–8 小时估计。规划每组只调用一次，比普通样本便宜 |
| 与 50k 的关系 | 可以复用 50k 已缓存的源记录，但要从 50k **没有用过**的源图里选，避免同一张图既出现在普通样本里、又出现在评测组里 |

## 9. 训练侧怎么用（供数据侧了解）

- **成对采样**：同一组的成员放进同一个 batch，输入是 no-ref 句子加各自的 token，目标是各自的目标图。约 15% 的行改用 ref 句子并去掉 token，保住纯文字指代的能力。
- **损失**：在执行区域内加权；另一个实例所在的区域作为"必须不变"的区域加权；注意力路由损失让图像 token 对正确的 token 注意力更高。
- **多指令训练**：合并目标配多句指令、多个 token，对应 benchmark 每图 2–5 条指令同时执行的设置。
- **评测**：用留出的 500 组衡量每个操作类型的"成对跟随率"和编辑质量。

## 10. 需要数据侧确认的问题

1. 同一宿主上的同类部件（左右袖子）在规划时能否稳定区分？如果 27B 规划的错指率高，这一类可以先不做。
2. 规划时把两个实例同时标在一张裁图上，裁图可能变大，小部件会不会因此看不清？必要时可以另给每个实例一张局部图。
3. 合并目标是否在本期一起做，还是由训练侧用交付的执行区域自行合成？训练侧可以自行合成，但数据侧一起做可以顺带审核边界。
4. 评测组的人工确认由谁完成、按什么标准记录。
