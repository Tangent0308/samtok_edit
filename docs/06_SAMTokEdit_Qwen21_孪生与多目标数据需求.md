# SAMTokEdit：反事实孪生与多目标编辑数据需求

- **日期**：2026-10-14。
- **读者**：数据侧，即 SA-1B 数据管线（仓库 `sam3-crispedit`，分支 `sa1b-samtok-edit-data`）。
- **一句话**：在同一张源图上，找两个同类实例，用**同一句 no-ref 指令**分别编辑，得到两张不同的目标图。这样模型只有读懂 prompt 里的 mask token，才能知道该改哪一个。
- **与现有数据的关系**：是 50k SA-1B 数据（`datasets/sa1b_samtok_edit_50k_20261014/`）的一个补充子集，训练部分 1.5 万组，约 3.2 万张目标图，约为 50k 的三分之二。生成和审核沿用 50k 的流程，主要改动在"选实例"和"规划"两步，另外加几条组级检查。
- **附加需求**：第 10 节是多目标联合编辑样本（同一张图 2–5 个目标，其中有相邻目标，链式生成），对应 benchmark 每图多条指令一起执行的主评测。第 1–9 节只讲孪生组。
- **依据**：方法侧的分析见 [03 v3 优化计划与进度](03_SAMTokEdit_Qwen21_v3优化计划与进度.md)；协议见 benchmark（v2branch）的协议文档，共享盘副本 `datasets/samtok_edit_benchmark_v2/docs/INSTRUCTION_PROTOCOL_ZH.md`（指令协议 1.0、mask 语义 1.1）。

## 1. 为什么需要这份数据

### 1.1 现有数据的退路

50k 数据里，每个 mask 单独规划一种编辑。所以同一张源图上的两条样本，指令文字几乎总是不同的：

| 源图 | 样本 1 | 样本 2 |
|---|---|---|
| 一张街景 | `Remove the selected umbrella.` | `Change the color of the selected window frame to green.` |

模型只看文字（"umbrella" 还是 "window frame"、删还是改色）就能分清要改哪里，并不需要去读 mask token。这条退路正是 v2 失败的原因：只用普通编辑对训练出来的 DiT 基本不看 token。同图同句只换 token 时，它的跟随率只有 0.06（文档 02 §4.2）。

### 1.2 孪生数据去掉退路

| | 实例 A | 实例 B |
|---|---|---|
| no-ref 指令 | `Change the color of the selected T-shirt to red.` | **逐字相同** |
| 模型实际看到的输入 | 源图 + 上句 + ⟨M_A⟩ | 源图 + 上句 + ⟨M_B⟩ |
| 目标图 | T_A：只有左边男士的 T 恤变红 | T_B：只有右边男士的 T 恤变红 |

两条输入只差 token，两张目标图却不同。模型要同时做对这两条，只能靠读 token。

### 1.3 用途

1. **训练**：两条放进同一个 batch，作为阶段 B 里"跟着 token 编辑"最直接的监督。
2. **评测**：留出一小部分组（200 组），衡量"换 token 后编辑是否跟着换"。现在只有 remove 有这样的探针，而且没有标准答案；有了这份数据可以扩展到四类操作，并且有目标图可以对照。

## 2. 一组样本的定义

- **一组**：1 张源图、2 个（少数 3 个）同类实例、1 份共用的编辑语义，以及每个实例各自的 ref、源 mask、执行区域和目标图。
- **组内共用**：操作类型、scope、payload、属性、附着关系，以及由它们渲染出的 no-ref 句子。
- **组内各自独有**：ref 短语（以及由它渲染出的 ref 句子）、源 mask、执行区域、目标图、审核结果。
- **每张目标图只改一个实例。** 其余实例必须与源图一致。
- **可选的合并目标**：把组内所有成员的编辑合在一张图上（见 5.3 节），用于多指令训练。不是必需项。

---

## 3. 怎样选实例

### 3.1 必须满足

1. **同一种 scope。** 两个实例在 no-ref 里用同一个名词，例如都是 `T-shirt`，都是 `chair`，都是 `front wheel`。只是类别相近不算，比如 `chair` 和 `stool`。
2. **都清晰可辨。** 两个都能单独用 ref 唯一地说出来，主体可见，不是严重失焦或几乎被挡住的碎片。
3. **互不重叠，执行区域也不重叠。** 各自扩出执行区域（50k 的 `target_plus_collar` 规则）之后，两个执行区域之间仍有间隔。建议间隔不小于两者中较小实例短边的 10%，且不少于 16 像素。这样两张目标图互不影响，也能合成合并目标。
4. **大小相近。** 两者面积比不超过 3。
5. **mask 质量合格。** 沿用 benchmark 的 mask 要求：保留可见像素和孔洞；不把整个人当成衣服；不覆盖邻近物体。
6. **与 benchmark 的 200 张源图不重叠。** 沿用 50k 的排除规则：按源图 ID 和原图字节哈希排除。

### 3.2 优先选的（越难越有价值）

- 外观相似的实例：同色同款的两把椅子、穿同样衣服的两个人。
- 位置相邻的实例：并排的两扇窗、相邻的两个人。
- **不同宿主上的同类部件**：两个人的袖子、两辆自行车的前轮。benchmark 大量考的是这种部件级目标。
- **同一宿主上的同类部件**：同一个人的左右袖子、同一扇门的两个把手。这类最难，但必须能用 image-left、image-right 之类的写法唯一指代。

### 3.3 必须排除

- **纹理类、成片的同类小物**：stone、stones、leaf、leaves、brick、tile、grass 等。统计已展开的 256 张源图，同类候选对里数量最多的正是这些类别，它们几乎无法做有意义的单独编辑。
- 一堆或一束同类物（按此前定的规则，算一个物体），不能拆成两个实例。
- 天空、地面、墙面这类背景大面。
- 同一个实物的碎块：被遮挡分成两块的同一物体只算一个实例，不能凑成一组。
- 删除不自然的部件，例如人的手臂、头。这一条与 50k 的 remove 规则相同。

### 3.4 尺寸与类别的分布

| 指标 | 目标 |
|---|---|
| 较小实例的面积占图 | 约 30% 小于 0.5%，40% 在 0.5–2%，30% 大于 2%。benchmark 的面积中位数是 0.57% |
| 部件级组（scope 是部件，例如 sleeve、handle、wheel） | 不少于 40% |
| 同一宿主上的同类部件 | 约 10% |
| 单个 scope 的占比 | 不超过 5%。避免被 person、window 之类的高频类别占满 |
| 每张源图 | 最多贡献 2 组，保证源图多样 |

## 4. 指令与标注

### 4.1 总要求

- 完全遵循指令协议 1.0、mask 语义 1.1、写作风格 `benchmark-concise-2-direct-add-1`，与 50k 数据和 benchmark 一致。
- **一组只做一次规划。** 规划模型同时看到组内全部实例（例如在裁图上用两种颜色分别标出 A 和 B），输出：
  - 一份**共用**的 `instruction_spec`（ref 字段除外）；
  - 每个实例各自的 ref。
- 共用的编辑必须**对每个实例都自然成立**。只适合其中一个时，拒绝这一组，不要硬造，也不要悄悄换成别的操作。
- no-ref 句子由共用的 spec 渲染，所以组内天然逐字相同；ref 句子由各自的 ref 渲染。
- 各自的 ref 要在组内互相区分：A 的 ref 不能同时指得通 B。
- payload 的值（新颜色、替换物、新增物）组内相同。这正是关键：同一个要求，作用在哪里只由 token 决定。

### 4.2 四类操作的写法

| 操作 | 共用的 no-ref 句子（示例） | 各自的 ref 句子（示例） | 要求 |
|---|---|---|---|
| attribute | `Change the color of the selected backpack to bright yellow.` | `…of the backpack on the left girl…` / `…of the backpack on the right girl…` | 新值要与两个实例原本的颜色都明显不同；不要选与其中一个原色相同的值 |
| replace | `Replace the selected stool with a wooden bar chair.` | `Replace the stool nearest the counter with…` / `Replace the stool by the window with…` | 替换物对两个位置的空间、支撑、视角都合适 |
| remove | `Remove the selected parked bicycle.` | `Remove the parked bicycle in front of the red door.` / `…in front of the shop window.` | 两个实例都适合删除，删除后的背景都能自然补全 |
| add | `Add a red knit beanie to the selected man.` | `…to the man on image-left.` / `…to the man on image-right.` | 两个宿主都是直接承载物（协议的直接锚点）；附着关系和位置对两者都成立。不使用参照式 add |

### 4.3 三实例组（可选，约占 15%）

规则与两实例相同，三个实例两两满足第 3 节的条件。一张源图上的三个 token 可以用于多指令训练和更难的评测。

## 5. 生成

### 5.1 沿用 50k 的流程

- 每个成员单独生成一次：围绕执行区域裁图，带区域权重编辑，按执行区域羽化贴回。
- 编辑器配置、40 步采样、内部编辑提示、执行区域规则都与 50k 相同。
- 组内各成员使用**相同的 seed**，使目标图之间的差别只来自"改哪个实例"。
- 生成时用各自的 ref 句子做编辑提示，与 50k 一致。训练时用 no-ref 句子加 token。

### 5.2 贴回带来的保证

因为是按执行区域贴回，T_A 里 B 的区域与源图逐像素相同，反过来也一样。这一点不需要额外检查，但要在记录里保留各自的执行区域和"区域外改动比例"，证明它成立。

### 5.3 合并目标（可选）

- **做法**：在源图上依次贴入每个成员的执行区域，得到一张"所有成员都改了"的图。
- **前提**：各执行区域互不重叠，并满足 3.1 节第 3 条的间隔。
- **注意**：这张图不再单独调用生成模型，所以要单独记一条"合并目标"，并在审核里检查边界处是否有光影冲突（第 6 节）。

## 6. 审核

### 6.1 单条审核：与 50k 相同

每个成员的目标图分别过一遍 50k 的确定性检查和 27B 语义审核：
- 目标是否完成；
- 非目标是否保持；
- 是否自然；
- 操作是否正确。

### 6.2 组级检查：新增

| 检查 | 要求 | 方式 |
|---|---|---|
| 句子相同 | 组内 no-ref 句子逐字相同；scope、操作、payload 相同 | 确定性 |
| 指代唯一 | A 的 ref 不能指向 B，反之亦然 | 27B 审核：给出全图和一个 ref，问它指的是标出的哪一个实例 |
| 都改了 | 每张目标图在自己的源 mask 内都有明显改动（不能一个改了、一个几乎没动） | 确定性：区域内改动比例，阈值与 50k 的 `inside_changed_fraction` 口径一致 |
| 改对了实例 | T_A 里 A 被改、B 不变；T_B 相反 | 确定性（贴回已保证另一实例不变）+ 27B 审核看完成度 |
| 结果可比 | 两张目标图的编辑效果相当，例如都变成了同一种黄色，替换物是同一种东西 | 27B 审核：把两张目标图的局部并排给它看 |
| 合并目标（若有） | 边界处无光影冲突、无断裂 | 27B 审核 + 抽查 |

**判定**：任一成员没有通过单条审核，或者任一组级检查不过，**整组丢弃**。单条合格的成员可以并入普通的 50k 池，但不再作为孪生组。

### 6.3 人工抽查

自动审核会误判（50k 验证批里，规划、成图目视、自动审核三项都通过的只有 66.7%）。发布前请按操作类型分层，抽查至少 200 组，记录指代、完成度和非目标保持三项的人工结论。评测留出的 200 组（第 8 节）要**全部**人工过一遍。

## 8. 规模、划分与交付

| 项 | 要求 |
|---|---|
| 规模 | 训练 **1.5 万组**（三实例组约占 15%，合计约 3.2 万张目标图）；评测 **200 组**（四类各 50 组）。训练部分建议分两批交付：先交 5,000 组，训练侧验证有效后再补齐，产能允许时可以继续扩到 2 万组以上 |
| 操作类型 | 四类各约 25% |
| 评测划分 | 评测组的源图与训练组、与 50k 数据的源图**都不重叠**；评测组每组都经过人工确认。评测组只做两实例组，不做合并目标 |
| 交付目录 | 按数据放置约定，在 `datasets/` 下新建一个子目录，例如 `datasets/sa1b_samtok_edit_twins_<日期>/`（尚不存在，待建），包含 `final/twins_train.jsonl`、`final/twins_eval.jsonl` 和 README |
| 估计耗时 | 50k 文档记载的生图吞吐约为每机每小时 737 条原始结果，4 机约 2,900 条。按组级通过率约 60% 估算（单条自动审核通过率约 87%，两实例组同时通过约 75%，再扣去组级检查），要生成约 5.4 万张原始目标图，生图约 19 小时；加上规划和冷启动，4 机约 1–1.5 天。第一批 5,000 组约需其三分之一。规划每组只调用一次，比普通样本便宜 |
| 与 50k 的关系 | **训练组**可以使用 50k 用过的源图（选不同的实例），也可以用 50k 已缓存但还没用到的源图；1.5 万组、每图最多 2 组，至少需要 7,500 张源图，50k 冻结的 1.6 万张源图够用。**评测组**必须用 50k 和训练组都没用过的源图，避免同一张图既出现在训练里、又出现在评测里 |

## 9. 训练侧怎么用（供数据侧了解）

- **成对采样**：同一组的成员放进同一个 batch，输入是 no-ref 句子加各自的 token，目标是各自的目标图。约 15% 的行改用 ref 句子并去掉 token，保住纯文字指代的能力。
- **损失**：在执行区域内加权；另一个实例所在的区域作为"必须不变"的区域加权；注意力路由损失让图像 token 对正确的 token 注意力更高。
- **多指令训练**：合并目标配多句指令、多个 token，对应 benchmark 每图 2–5 条指令同时执行的设置。
- **在阶段 B 里的比例**：孪生组约占训练行的 20–25%，其余是 50k 单条编辑、多指令合成样本、v1 清洗数据和少量指认任务。孪生数据只教"改哪一个只能看 token"，编辑质量主要靠 50k，所以不单独使用。
- **评测**：用留出的 200 组衡量每个操作类型的"成对跟随率"和编辑质量。它是开发过程中的诊断集，论文主结果仍然是 benchmark v2。

## 10. 附加需求：多目标联合编辑样本

### 10.1 为什么需要

benchmark 的主评测是"每张图 2–5 条指令写在一个 prompt 里一起执行，全部做对才算通过"。模型要学会两件事：
- 一句话里出现多个 token 时，各自的编辑落在各自的区域；
- 几处编辑互不干扰，也不漏掉任何一条。

多目标训练样本有两个来源：

| 来源 | 做法 | 谁来做 | 覆盖不到什么 |
|---|---|---|---|
| A. 拼合样本 | 同一张源图上，50k 和孪生组里多条合格的单目标样本，把各自执行区域内的结果贴到同一张图上 | **训练侧自己做**，不需要新数据 | 为避免互相干扰，要求执行区域之间留出间隔，所以覆盖不到挨在一起的目标 |
| B. 链式生成的紧邻多目标 | 同一张图上选 2–5 个目标，其中至少一对相邻，按顺序逐个编辑，后一步在前一步的结果上做 | **数据侧生成**（本节的需求） | — |

benchmark 里 199/200 张图标有"紧邻保护"，很多目标挨在一起，例如同一个人的袖子和包带、手和手里拿的东西、并排的两个人。这类组合拼合样本做不了，需要 B。

**对 50k 数据的唯一要求**：保留每条样本的执行区域（`support_mask`），并保持"执行区域外与源图逐像素相同"。现在已经满足，拼合样本靠它保证精确。

### 10.2 一组样本的定义

- **一组**：1 张源图、2–5 个目标，每个目标一种操作、一条指令，最后得到一张"所有目标都改完"的联合目标图。
- **每个目标独立**：各有源 mask、ref、ref 句子、no-ref 句子、`instruction_spec`、执行区域。
- **指令都对原图而写**：指代和 mask 都以**原始源图**为准，不能依赖其他目标改完之后的样子。例如不能写 "the newly added hat"。
- **联合目标图里**：每个目标都完成了自己的编辑；所有目标的执行区域之外，与源图一致。
- 交付各步的中间图（见 10.6）。

### 10.3 怎样选目标

**必须满足**
1. 每个目标单独看，都满足 50k 的选择和协议要求：可唯一指代、mask 合格、操作自然。
2. **至少一对目标相邻**：两者的执行区域相接，或间隔不超过较小目标短边的 10%。其余目标可以离得远。
3. **目标之间没有冲突。**
   - 一个目标的执行区域不能盖住另一个目标的源 mask 的主体（建议重叠不超过后者面积的 10%）。
   - 不能出现"删掉一个人"同时"给这个人的衣服改色"这类逻辑冲突。
   - 同一个实物上可以有多个目标，但必须是不同部件，且彼此不重叠。例如同一个人的袖子改色、背包带上加挂件。
4. 不同目标是不同的实物或不同的部件，不能把同一个物体的碎块算成多个目标（与 benchmark 的入选标准相同）。
5. 源图不在 benchmark 的 200 张里；评测组的源图不在任何训练数据里。

**操作组合**（与 benchmark 的组合规则一致）
- 2–4 个目标的组：操作类型不重复。
- 5 个目标的组：四类都有，其中一类重复。
- 整体上四类操作各约 25%。

**目标数分布**：2 个约 20%，3 个约 30%，4 个约 25%，5 个约 25%。比 benchmark（5 个目标的占 42.5%）略偏少目标，便于从易到难训练。

**优先选的**
- 同一宿主上的不同部件：同一个人的上衣和包带。
- 手和所持物、人和座椅这类接触关系。
- 同类相邻实例分别做不同操作：左边的椅子删掉，右边的椅子改色。

**面积**：沿用孪生需求 3.4 节的分布（约 30% 小于 0.5%）。

### 10.4 规划

- **一组只调用一次规划**：规划模型看全图，图上用不同颜色标出全部候选 mask，按 10.3 的规则选出目标，并为每个目标写出完整的 `instruction_spec` 和 ref。
- 每个目标的 ref 必须在**原图**上唯一，并且与组内其他目标互相区分。
- 规划同时给出**生成顺序**。建议先做 remove，再做 replace，然后 attribute，最后 add：先把要删的东西删掉，后面的编辑在更干净的画面上进行；add 放最后，避免新增物被后续编辑改动。
- 规划不出满足条件的组合时，拒绝这张图，不要降低条件。

### 10.5 生成：链式执行

1. 第 1 个目标：在源图上按 50k 的流程编辑（裁图、带区域权重编辑、按执行区域贴回），得到中间图 1。
2. 第 k 个目标：在中间图 k−1 上编辑。裁图取自中间图 k−1，执行区域和源 mask 仍用原图上的几何；贴回也贴在中间图 k−1 上，得到中间图 k。
3. 最后一张中间图就是联合目标图。
4. 所有步骤用同一个 seed，编辑器配置与 50k 相同。

这样，后一步看到的是前一步改过的画面，相邻处的光影、遮挡、接触关系自然一致；拼合样本做不到这一点。

### 10.6 审核

**每一步**：对中间图 k 做 50k 的单条审核：目标完成、非目标保持、自然、操作正确。这里的"非目标保持"只看本步，前面步骤的改动视为已允许。

**整组**：在联合目标图上，对照原图逐个目标检查。

| 检查 | 要求 |
|---|---|
| 每个目标都完成 | 后面的步骤没有把前面的编辑改坏或抹掉。重点看相邻目标 |
| 没有串扰 | 某一步的编辑没有落到另一个目标的区域里，例如 attribute 的新颜色没有染到相邻目标上 |
| 整图保持 | 所有执行区域之外与源图一致（确定性检查） |
| 整图自然 | 相邻编辑之间的边界、光影、接触合理 |
| 指代唯一 | 每个 ref 在原图上只指向自己的目标，与组内其他目标不混淆 |

**判定**：任一步或任一整组检查不过，整组丢弃，不退化成目标更少的组。单步合格的结果不并入 50k 池，因为它是在中间图上做的，不是在原图上做的。

**人工抽查**：按目标数分层抽查不少于 100 组；评测组全部人工确认。

### 10.7 交付字段

| 层级 | 字段 | 说明 |
|---|---|---|
| 组 | `multi_id`、`source_id`、`source_image`、`source_provenance` | 与 50k 相同 |
| 组 | `n_targets`、`operations` | 目标数与各目标的操作 |
| 组 | `generation_order` | 实际生成顺序（目标编号的列表） |
| 组 | `adjacent_pairs` | 相邻的目标对及其间隔 |
| 组 | `joint_target`、`joint_audit` | 联合目标图和整组检查结果 |
| 组 | `split` | `train` 或 `eval` |
| 目标 | `unit_id`、`object_id`、`ref`、`instruction`、`instruction_noref`、`instruction_spec` | 与单目标样本相同 |
| 目标 | `mask`、`bbox`、`point`、`support_mask`、`area_fraction` | 都以原图为准 |
| 目标 | `step_input_image`、`step_output_image`、`generation_context`、`step_audit` | 该步的输入图、输出图、生成记录和审核 |

### 10.8 规模与耗时

| 项 | 要求 |
|---|---|
| 训练 | **5,000 组**（平均约 3.6 个目标，约 1.8 万步生成）。分两批：先交 1,500 组，训练侧验证有效后再补齐 |
| 评测 | **100 组**，目标数分布与训练相同，全部人工确认；源图不在任何训练数据里 |
| 耗时 | 整组通过率按约 45% 估算（单步约 87%，3.6 步全部通过约 60%，再扣掉整组检查），约需 4 万步原始生成。按 4 机每小时约 2,900 步，生图约 14 小时；链式生成同一组内的步骤必须串行，但不同组可以并行，对总吞吐影响不大。加上规划和冷启动，4 机约 1 天 |
| 优先级 | 低于孪生组的第一批（5,000 组）。可以在孪生第一批交付后开始 |

### 10.9 训练侧怎么用（供数据侧了解）

- **阶段 A'**：多 token 指认（一句话 2–5 个 token，各涂一种颜色）由训练侧程序生成，不需要数据侧参与。
- **阶段 B 前期**：多目标样本约占 10%，只用 2–3 个目标，以拼合样本为主。
- **阶段 B 后期**：单目标指标达标后提到 20–30%，加入 4–5 个目标和链式生成的紧邻样本。
- **prompt**：多条指令按编号逐行写进一个 prompt，每条带自己的 token。训练时随机打乱顺序，目标图不变。每条随机使用 no-ref 加 token、ref 加 token 或只有 ref，与 benchmark 的混合定位形式对应。
- **评测**：100 组留出样本衡量整图通过率和串扰率，用来比较"一次联合执行"和"逐条顺序执行"两种推理方式。

## 11. 需要数据侧确认的问题

**孪生组**
1. 同一宿主上的同类部件（左右袖子）在规划时能否稳定区分？如果 27B 规划的错指率高，这一类可以先不做。
2. 规划时把两个实例同时标在一张裁图上，裁图可能变大，小部件会不会因此看不清？必要时可以另给每个实例一张局部图。
3. 合并目标是否在本期一起做，还是由训练侧用交付的执行区域自行合成？训练侧可以自行合成，但数据侧一起做可以顺带审核边界。
4. 评测组的人工确认由谁完成、按什么标准记录。

**多目标组**

5. 在中间图上继续编辑时，区域权重和贴回是否需要改动？现有流程默认输入就是原图。

7. 10.4 节建议的生成顺序（remove → replace → attribute → add）是否合理，有没有你们验证过的更好的顺序？
